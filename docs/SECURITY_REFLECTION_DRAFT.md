# Security Reflection Draft

I implemented several basic security controls for this Vue front-end coursework application, while recognising that it is not production-grade authentication or authorisation. For XSS prevention, I rely on Vue's default text interpolation and do not use `v-html`, `innerHTML`, `eval`, or similar dangerous DOM execution patterns. User-controlled values such as names, appointment notes, search text, and ratings are validated or normalised before use, and they are rendered as text rather than executable HTML.

For authentication, ordinary user passwords are not stored in plain text. The app uses the browser Web Crypto API with PBKDF2, SHA-256, and a random salt, then stores only the hash and salt. The session is deliberately small and stores only `userId` and `createdAt`, not passwords, hashes, salts, or roles. Route guards and function-level checks protect profile, appointment, admin, and rating actions. I also added ownership checks so users can only work with their own appointments and ratings, and I added Local Storage parsing fallbacks so corrupted JSON does not crash the app.

The main limitation is that this is a pure front-end demo. Local Storage can be inspected or changed by someone with access to the browser, so true authentication and authorisation must be enforced by a trusted server. The fixed demo admin credential is public coursework data and cannot be treated as secret. For production, I would move accounts, sessions, ratings, and appointments to a backend API with server-side validation, secure database storage, server-side RBAC, HTTPS, HttpOnly/Secure/SameSite cookies, proper security headers, key management, logging, and audit trails.
